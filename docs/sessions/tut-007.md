## The big picture (read this first)

In RAG, files are not “just files on disk.” They are **resources belonging to a project**. You need to:

- know **which files** a project has
- avoid losing track when filenames are UUIDs on disk
- link every **chunk** back to the file it came from

So the flow becomes:

```text
Upload
  → save bytes to disk
  → insert a row in `assets` (metadata)
  → return the asset’s Mongo `_id`

Process
  → look up asset(s) for the project
  → load each file from disk by `asset_name`
  → split into chunks
  → save chunks with `chunk_project_id` + `chunk_asset_id`
```

Think of **disk** as the warehouse and **Mongo assets** as the inventory system.

## Lesson 1 — The Asset model

**File:** `src/models/db_schemes/asset.py`

An asset is metadata about something you uploaded:

| Field | Meaning |
|-------|---------|
| `asset_project_id` | Which project owns this file |
| `asset_type` | Kind of asset (for now: `"file"`) |
| `asset_name` | Filename on disk (the generated `file_id`) |
| `asset_size` | Size in bytes |
| `asset_config` | Optional extra settings (for later) |
| `asset_pushed_at` | When it was recorded |

**Tutor tip:** `asset_name` is the name on **disk**. The Mongo `_id` is how the **API/database** refer to the asset. Don’t mix them up when you debug.

### Why `AssetTypeEnum`?

Today everything is a file. Tomorrow you might store URLs, images, or other types. An enum keeps `"file"` consistent instead of scattering magic strings.

## Lesson 3 — Indexes (don’t skip this)

Indexes make lookups fast and can enforce uniqueness.

Each schema now has a classmethod `get_indexes()`. Models use:

```text
create_instance() → init_collection() → create_index(...)
```

So the first time you use a collection, indexes are created if they don’t exist yet.

### What we index

| Collection | Index | Why |
|------------|-------|-----|
| `projects` | unique on `project_id` | one logical project id → one document |
| `chunks` | on `chunk_project_id` | “all chunks for this project” is a common query |
| `assets` | on `asset_project_id` | “all files for this project” |
| `assets` | **unique** on `(asset_project_id, asset_name)` | same disk filename can’t be registered twice in one project |

**Mental model:** without an index, Mongo may scan many documents. With an index, it jumps to the matching keys. Unique indexes are also **rules**: the database rejects duplicates for you.

## Lesson 4 — Chunks remember their file

**File:** `src/models/db_schemes/data_chunk.py`

New field:

```text
chunk_asset_id: ObjectId
```

Previously a chunk only knew its **project**. Now it also knows its **source file**.

Why that matters:

- multi-file projects (“which chunks came from report.pdf?”)
- re-processing one file later
- deleting or replacing one file’s chunks without touching the others (future work)

## Lesson 5 — Upload route: disk + database

**File:** `src/routes/data.py` → `POST /upload/{project_id}`

After validation and writing the file to disk:

1. Build an `Asset` (`type=file`, `name=file_id`, `size=...`)  
2. `create_asset(...)`  
3. Response returns `"file_id": str(asset_record.id)` — the **Mongo asset id**

**Checkpoint question:**  
If you open the project folder on disk, do you see the Mongo `_id` as the filename?  
→ No. Disk still uses the generated name (`asset_name`). The response’s `file_id` is the asset’s `_id` in this session’s design — when you process, pay attention to whether the client sends the disk name or the Mongo id (see Lesson 6).

## Lesson 6 — Process route: one file or all files

**Request body** (`ProcessRequest`):

- `file_id` is now **optional** (`None` by default)  
- `chunk_size`, `overlap_size`, `do_reset` stay as before  

### Behavior

| Client sends | Server does |
|--------------|-------------|
| `file_id` present | Look up that asset; process only that file |
| `file_id` omitted | Load **all** `FILE` assets for the project; process each |

For each file:

1. Load content (`ProcessController`)  
2. Split into chunks  
3. Build `DataChunk` rows with `chunk_project_id` **and** `chunk_asset_id`  
4. Insert into Mongo  

Response:

```json
{
  "signal": "processing_success",
  "inserted_chunks": <number>,
  "processed_files": <number>
}
```

New error signals:

- `NO_FILES_ERROR` — project has no assets to process  
- `FILE_ID_ERROR` — the given file id/name was not found  

**Tutor tip:** `do_reset=1` still deletes **all** chunks for the project before inserting. In a multi-file run, that means a full project reset, not “reset only this file.” Notice that design choice; it’s simple for learning, not the final production rule.

## Lesson 7 — Safer file loading

**File:** `src/controllers/ProcessController.py`

If the path does not exist, return `None` instead of crashing.  
The process loop logs the error and **continues** to the next file.

That’s real-world thinking: one missing file shouldn’t kill the whole batch.

## Lesson 8 — Docker: auth + named volume

**Files:** `docker/docker-compose.yml`, `docker/.env.example`

Changes:

1. Volume `mongodata:` instead of bind-mount `./mongodb`  
2. `MONGO_INITDB_ROOT_USERNAME` / `MONGO_INITDB_ROOT_PASSWORD` from env  

**Why:** named volumes are the usual Docker way to persist DB data; root credentials stop running Mongo wide open in local setups.

Setup reminder:

```bash
cd docker
cp .env.example .env
# fill username/password
docker compose up -d
```

Update app `MONGODB_URL` if auth is required (credentials in the connection string).
