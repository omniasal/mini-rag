# Session 5 (`tut-005`) — Process an Uploaded File

> **Previous session:** `tut-004` — you **upload** a file into a project folder on disk and get back a `file_id`.  
> **This session:** take that file, **load** its text, **split** it into chunks, and return those chunks from a new API endpoint. This is the “R” preparation step in RAG: turn documents into pieces you can later embed and search.

---

## Learning goals

By the end of this session you should be able to answer:

1. Why do we split documents into chunks instead of embedding the whole file?
2. What is a **document loader**, and why does `.txt` use a different loader than `.pdf`?
3. What do `chunk_size` and `chunk_overlap` mean?
4. How does the new `/process/{project_id}` endpoint connect to the upload flow?
5. What role does LangChain play here?

---

## The big picture (read this first)

Upload alone is not enough for RAG. A PDF or long text is too big to stuff into a prompt or embed as one blob. You need smaller, overlapping pieces:

```text
tut-004:  Upload → file on disk → file_id

tut-005:  Process → load file → list of Documents → split → list of chunks → return JSON
```

Typical client flow:

1. `POST /api/v1/data/upload/{project_id}` → get `file_id`  
2. `POST /api/v1/data/process/{project_id}` with that `file_id` → get chunks  

**Tutor tip:** In this session chunks are **returned in the response only**. They are not saved to a database yet — that comes in `tut-006`. First learn the pipeline; then persist it.

## Lesson 2 — `ProcessingEnum`: which file types we can process

**File:** `src/models/enums/ProcessingEnum.py`

```text
TXT = ".txt"
PDF = ".pdf"
```

The controller picks a loader from the file extension. If the extension is neither, there is no loader (`None`).

**Tutor tip:** Upload validation (allowed types) and process loaders should stay aligned. If you allow a type on upload but have no loader, process will fail later.

## Lesson 3 — `ProcessRequest`: the process API body

**File:** `src/routes/schemes/data.py`

| Field | Default | Meaning |
|-------|---------|---------|
| `file_id` | required | Disk filename returned from upload |
| `chunk_size` | `100` | Max characters per chunk (with `len` as length function) |
| `overlap_size` | `20` | Characters shared between neighboring chunks |
| `do_reset` | `0` | Reserved for later (used when saving to DB in tut-006) |

Example body:

```json
{
  "file_id": "abc123_notes.txt",
  "chunk_size": 100,
  "overlap_size": 20
}
```

**Why overlap?** So a sentence that sits on a boundary isn’t cut in half with no context in either chunk. Overlap is a small “glue” between pieces.

---

## Lesson 4 — `ProcessController`: the heart of this session

**File:** `src/controllers/ProcessController.py`

Extends `BaseController`. On init it remembers `project_id` and resolves the project folder via `ProjectController().get_project_path(...)`.

### Step A — Pick a loader (`get_file_loader`)

```text
file path = project_path / file_id

if extension == .txt → TextLoader(...)
if extension == .pdf → PyMuPDFLoader(...)
else → None
```

### Step B — Load content (`get_file_content`)

```text
loader.load() → list of Document objects
```

Each LangChain `Document` typically has:

- `page_content` — the text  
- `metadata` — e.g. source path, page number for PDFs  

### Step C — Split (`process_file_content`)

Uses `RecursiveCharacterTextSplitter`:

- `chunk_size` / `chunk_overlap` from the request  
- `length_function=len` — size counted in characters  

It:

1. Pulls all `page_content` strings  
2. Pulls matching `metadata` dicts  
3. Calls `create_documents(texts, metadatas=...)`  
4. Returns a new list of smaller `Document` chunks  

**Why “Recursive” character splitter?** It tries to split on nice boundaries (paragraphs, sentences, words) before falling back to hard cuts — better chunks than blindly slicing every N characters.

---

## Lesson 5 — The new route

**File:** `src/routes/data.py`  
**Endpoint:** `POST /api/v1/data/process/{project_id}`

Flow:

1. Read `file_id`, `chunk_size`, `overlap_size` from body  
2. Build `ProcessController(project_id=...)`  
3. `get_file_content(file_id)`  
4. `process_file_content(...)`  
5. If no chunks → `400` + `PROCESSING_FAILED`  
6. Else → **return the chunk list directly** (FastAPI serializes the Documents)

**Contrast with upload:** upload writes bytes and returns a small signal JSON. Process returns the **data product** of this stage: the chunks themselves (great for learning and Postman inspection).

### A. Chunking & document processing (anchored in tut-005)

**Q1. Why chunk at all? Why not embed the whole document?**

**A:** Embedding models and LLM context windows have limits; retrieval needs *local* semantic units. One giant vector averages many topics and retrieves poorly (“lost in the middle” / diluted similarity). Chunks trade **recall of specific facts** for **more vectors and more index cost**. Seniors also mention: chunking strategy is a product decision (FAQ vs legal docs vs code), not a library default.

**Q2. Character-based `chunk_size` vs token-based sizing — tradeoff?**

**A:** This tutorial uses `length_function=len` (characters). Production usually sizes by **tokens** to match the embedding model’s tokenizer and max input. Characters are simple and language-agnostic to implement; they drift from real model limits (especially multilingual or code). Interview signal: “I’d align chunk size with the embedding model’s token limit and leave headroom for instructions.”

**Q3. What does overlap buy you, and what does it cost?**

**A:** Overlap reduces boundary cuts (a sentence split across two chunks). Cost: **duplicate text** → more storage, more embeddings, possible duplicate hits in retrieval (need dedup / MMR / score fusion later). Too much overlap → redundancy; too little → broken context. Typical senior range talk: 10–20% of chunk size as a starting heuristic, then evaluate on a golden question set.

**Q4. `RecursiveCharacterTextSplitter` vs fixed-size vs semantic / structure-aware chunking?**

**A:**

| Strategy | Pros | Cons |
|----------|------|------|
| Fixed size | Simple, predictable | Cuts mid-sentence / mid-table |
| Recursive (separators) | Better boundaries, still cheap | Still blind to meaning |
| By headings / pages / sections | Respects document structure | Needs parsers; uneven sizes |
| Semantic (embedding breakpoints) | Topic-coherent chunks | Expensive; harder to tune |

Course choice (recursive) is the right **MVP**. Senior follow-up: for PDFs with tables, layout-aware parsing beats any splitter.

**Q5. TXT loader vs PDF loader — what can go wrong in production?**

**A:** PDFs are not “text files with pages.” Risks: scanned PDFs (need OCR), multi-column layout, headers/footers noise, encrypted files, huge memory on `loader.load()`. TXT has encoding issues (`utf-8` vs `latin-1`). Senior answer: validate file type by **content** (magic bytes), not only extension; stream/page-batch large PDFs; separate OCR path.

**Q6. Why is returning raw chunks from `/process` fine for learning but bad as a public API?**

**A:** Large payloads, tight coupling to LangChain `Document` shape, no persistence, no idempotency, easy to DoS the API with big files. Production: accept job → process async → store chunks → return `job_id` / counts. The course later moves to Mongo insert summaries, then Celery — that’s the maturation path. Say that explicitly.

**Q7. Upload and process are separate HTTP calls. Sync vs one combined endpoint?**

**A:**

- **Split (course style):** clearer stages, retry process without re-upload, progress UX.  
- **Combined:** fewer round-trips, harder partial failure semantics.  
- **Async job:** required at scale either way.

Senior framing: separate commands (upload asset, index asset) match CQRS-ish thinking; couple them only behind an orchestration workflow (later: Celery).

### B. API & backend design (tut-004 → tut-007)

**Q8. Why `project_id` in the path instead of only in the body?**

**A:** Resources are naturally nested (`/data/.../{project_id}`). Path IDs make caching, authz (“can this user touch this project?”), and logs easier. Body carries *operation parameters* (`chunk_size`), not the resource identity. Classic REST taste.

**Q9. Signal enums (`FILE_UPLOAD_SUCCESS`, `PROCESSING_FAILED`) vs HTTP status only vs RFC7807 problem+json?**

**A:** Course uses **HTTP status + app-level signal string** — easy for clients and teaching. Tradeoff: signals can drift from HTTP semantics; clients must understand a custom vocabulary. Production often standardizes on problem details + stable error codes. Don’t dismiss the enum pattern: stable machine-readable codes beat free-text errors.

**Q10. `do_reset` deleting all project chunks — what’s wrong at scale?**

**A:** It’s a blunt global wipe. Multi-file projects (tut-007) still reset **everything** when you meant one file. Senior design: reset by `asset_id` / version; soft-delete; or immutable versions (`index_v3`) and point the project to the active version. Also: delete + re-insert should be transactional or orchestrated so readers never see empty index mid-job.

**Q11. Disk file + Mongo asset metadata (tut-007) — why both?**

**A:** Blob storage (disk/S3) is for **bytes**; DB is for **queryable metadata** and relationships (project → assets → chunks → vectors). Don’t store large binaries in Mongo/Postgres as the default. Tradeoff of local disk (course): simple, not HA, not multi-instance safe — production uses object storage + DB pointer.

**Q12. Why index `(asset_project_id, asset_name)` uniquely?**

**A:** Enforces an invariant: one registered name per project. Prevents duplicate catalog rows when clients retry uploads. Interview depth: uniqueness ≠ idempotent upload of *content*; you may still want checksum-based dedup (`content_hash`) so the same PDF uploaded twice doesn’t double-index.

**Q13. Controllers vs routes vs models — defend the layering.**

**A:**

- **Routes:** HTTP, validation, status codes  
- **Controllers:** use-case / domain orchestration (paths, loaders, splitting)  
- **Models:** persistence  

Keeps FastAPI handlers thin and makes Celery tasks reuse the same controller/service later. Smell to call out: fat routes that import loaders directly become untestable.

### C. Data stores & evolution (tut-006 → tut-014)

**Q14. Why Mongo first, then Postgres (+ Alembic), then maybe pgvector?**

**A:** Mongo is fast for evolving document shapes (chunks with free-form metadata) during learning. Postgres wins for **transactions, migrations, joins, constraints**, ops maturity. pgvector keeps vectors **next to** relational data (one system); Qdrant is a **specialized** vector store (HNSW tuning, filtering, scale). Senior answer: start specialized or colocated based on team ops skill and filtering/transaction needs — not hype.

**Q15. Motor async Mongo in FastAPI — why not sync PyMongo?**

**A:** Sync calls block the event loop under concurrent load. Motor fits `async def` routes. Tradeoff: async spreads through the stack; mixing sync CPU-heavy PDF parsing inside async routes still blocks — offload to thread pool or workers (Celery). That’s a classic FastAPI footgun.

**Q16. Storing `chunk_project_id` / `chunk_asset_id` as ObjectIds — why?**

**A:** Stable foreign-key-like references to parent documents. String `project_id` from the URL is a business key; ObjectId is the surrogate. Later SQL world: integer/UUID FKs + migrations. Interview: always know which ID is **business** vs **surrogate**.

**Q17. What breaks if you re-chunk with new `chunk_size` but leave old vectors?**

**A:** Embedding index no longer matches the chunk table (orphan vectors, missing vectors, wrong text). You need a **versioned index** or delete-by-asset then re-embed. Pipeline consistency (chunks ↔ embeddings ↔ vector collection name) is a senior RAG ops topic.

### D. LLM, embeddings & RAG quality (tut-008 → tut-012)

**Q18. Why a provider factory (OpenAI / Cohere / …) instead of calling one SDK everywhere?**

**A:** Swap vendors, mock in tests, separate **embedding model** from **chat model**. Tradeoff: abstraction can leak (different token limits, metadata). Good factories expose small interfaces: `embed_documents`, `generate`. Course pattern is textbook dependency inversion.

**Q19. Chunk size vs embedding model vs retrieval k — how do they interact?**

**A:** Small chunks → precise retrieval, may need larger `k` or neighbor expansion. Large chunks → more context per hit, noisier similarity. `k` too high → context stuffing and cost. Senior workflow: fix models → build eval set → sweep chunk size / overlap / k → measure answer quality + latency + $.

**Q20. What failure modes does “stuff top-k chunks into the prompt” have?**

**A:** Irrelevant chunks, contradictory sources, context overflow, citation hallucination, prompt injection via documents. Mitigations: metadata filters, rerankers, MMR, grounded prompts (“answer only from context”), citation requirements, max context budget. Show you don’t think RAG is “embed + cosine + done.”

**Q21. When is RAG the wrong tool?**

**A:** Stable small knowledge that fits a system prompt; tasks needing deep multi-hop reasoning over implicit knowledge; when you need exact transactional answers (use DB/SQL tools). Seniors choose among fine-tuning, tools/agents, RAG, or plain software.

### E. Async jobs, scale & production (tut-015 → tut-017)

**Q22. Why move file processing to Celery (Redis/RabbitMQ)?**

**A:** PDF load + split + embed can take seconds–minutes; HTTP workers shouldn’t hold that. Queue gives retries, concurrency control, horizontal scale. Tradeoffs: operational complexity, at-least-once delivery → **idempotency** (course later adds execution tracking). Interview gold: “exactly-once” is usually “at-least-once + idempotent handlers.”

**Q23. What would you monitor in this system?**

**A:** Upload size/reject rate; process duration; chunk counts per file; embedding tokens/$/latency; vector upsert failures; RAG answer latency; queue depth; worker errors; duplicate job rate. Product metrics: retrieval hit relevance, groundedness, user thumbs-down.

**Q24. Security concerns you’d raise in a design review of mini-rag?**

**A:** Authn/z per project; path traversal on `file_id`; unrestricted upload size/type; SSRF if you later fetch URLs; prompt injection from documents; secret management in `.env`; Mongo exposed without auth (early docker); PII in chunks/logs; tenancy isolation in vector collections.

### F. “Compare two designs” rapid-fire (strong senior signal)

**Q25. Local disk vs S3/MinIO for uploaded files?**  
**A:** Local = simple, single-node. Object storage = durable, multi-instance, lifecycle policies. API should store a URI, not assume `./assets`.

**Q26. Sync `/process` returning chunks vs enqueue + webhook/poll?**  
**A:** Sync for demos and tiny files; async for anything user-facing at scale.

**Q27. Qdrant vs pgvector?**  
**A:** Qdrant: vector-first features/scale. pgvector: fewer moving parts if Postgres is already SOFT (source of truth). Hybrid is common: Postgres metadata + specialized vector DB.

**Q28. Character splitter now vs “we’ll fix chunking later”?**  
**A:** Acceptable for MVP if you **version** the index and can repipeline. Dangerous if you ship embeddings to production with no reindex plan.

**Q29. What would you change first in tut-005 code in a production PR?**  
**A:** (Pick 2–3) Guard missing files; don’t return full chunks; cap file size/time; run CPU parsing off the event loop; authenticate project access; make process idempotent; add structured logging/metrics; content-type sniffing.

**Q30. Explain end-to-end RAG data flow as if to another senior.**  
**A:** *User uploads bytes → object store + asset row → worker extracts text → chunker emits versioned chunks → embedder writes vectors keyed by chunk/asset/project → query embeds question → ANN search + filters → optional rerank → LLM grounded on retrieved text → answer + citations. Control plane (API) and data plane (workers/vector) stay separated.*
