# Session 6 (`tut-006`) — Push Projects & Chunks into MongoDB

> **Previous session:** `tut-005` — you **process** an uploaded file (load + split into chunks) and return chunks from the API.  
> **This session:** stop throwing chunks away after the response. Store **projects** and **chunks** in **MongoDB**, and wire the app to a real database via Docker.

---

## Learning goals

By the end of this session you should be able to answer:

1. Why does a RAG app need a database at all?
2. What is the difference between a **Pydantic schema** and a **data model** (Model class) here?
3. How does FastAPI get a Mongo connection on startup?
4. What does `get_project_or_create_one` do, and why call it on upload *and* process?
5. Why insert chunks in **batches** (`bulk_write`) instead of one-by-one only?

---

## The big picture (read this first)

Until now, processing lived only in memory for one request:

```text
Upload → file on disk
Process → load file → split → return chunks in JSON  ← then gone
```

For RAG you need those chunks later (embedding, search, answer). So:

```text
Upload  → ensure Project exists in Mongo → file on disk
Process → ensure Project exists
        → split file into chunks
        → save DataChunk documents in Mongo
        → return how many were inserted
```

**Tutor tip:** Disk still holds the raw file. Mongo holds **structured pieces** (chunks) tied to a **project**. Two storages, two jobs.

## Lesson 1 — Run Mongo with Docker Compose

**File:** `docker/docker-compose.yml`

A service named `mongodb`:

- Image: `mongo:7-jammy`
- Host port **27007** → container **27017** (so it won’t clash with a local Mongo on 27017)
- Data folder: `./mongodb` bind-mounted to `/data/db`
- Network: `backend`
- `restart: always`

**How to start it:**

```bash
cd docker
docker compose up -d
```

Then in `src/.env`:

```text
MONGODB_URL=mongodb://localhost:27007
MONGODB_DATABASE=mini_rag   # or any name you choose
```

**Checkpoint:** After `docker compose up -d`, can you reach Mongo on port `27007`? If the app can’t connect, check the URL and that the container is running.

## Lesson 3 — Connect on startup (Motor)

**File:** `src/main.py`  
**Library:** `motor` = async MongoDB driver for asyncio / FastAPI

```text
startup:
  app.mongo_conn = AsyncIOMotorClient(MONGODB_URL)
  app.db_client  = app.mongo_conn[MONGODB_DATABASE]

shutdown:
  app.mongo_conn.close()
```

Routes get the DB via `request.app.db_client` (they inject `Request`).

**Why Motor, not sync PyMongo alone?** FastAPI endpoints are `async`. Motor lets you `await` DB calls without blocking the event loop.

**Tutor tip:** `mongo_conn` is the **client** (connection). `db_client` is one **database** inside that server. Collections hang off the database.

## Lesson 4 — Schemas vs Models (architecture)

This session introduces a clean split. Don’t blur them:

| Layer | Role | Examples |
|-------|------|----------|
| **Schema** (`db_schemes/`) | Shape of a document (fields, validation) | `Project`, `DataChunk` |
| **Model** (`ProjectModel`, `ChunkModel`) | How to **create / read / delete** in Mongo | `create_project`, `insert_many_chunks` |
| **BaseDataModel** | Shared: hold `db_client` + settings | parent class |

### Project schema

**File:** `src/models/db_schemes/project.py`

- `_id` → optional `ObjectId` (Mongo’s id), alias `_id`
- `project_id` → your string id from the URL (must be **alphanumeric**)

### DataChunk schema

**File:** `src/models/db_schemes/data_chunk.py`

| Field | Meaning |
|-------|---------|
| `chunk_text` | The text piece |
| `chunk_metadata` | Loader metadata (e.g. source info) |
| `chunk_order` | Position in the file (`> 0`) |
| `chunk_project_id` | Mongo `_id` of the **Project** document |

**Important:** `chunk_project_id` stores the project’s Mongo `ObjectId` (`project.id`), not the string `"myproject"` from the URL. That links chunks to the project document reliably.

### Collection names

**File:** `src/models/enums/DataBaseEnum.py`

- `projects`
- `chunks`

Enums avoid typos like `"projets"` vs `"projects"`.

## Lesson 5 — ProjectModel

**File:** `src/models/ProjectModel.py`

Key method: **`get_project_or_create_one(project_id)`**

1. Look up `{ "project_id": project_id }`  
2. If missing → create a `Project` and insert it  
3. Return the `Project` (with its Mongo `_id`)

Also:

- `create_project`
- `get_all_projects(page, page_size)` — pagination with `skip` / `limit`

**Why call this on upload and process?**  
Either endpoint might be the first time you see that `project_id`. The project row must exist before you attach chunks to `project.id`.

---

## Lesson 6 — ChunkModel

**File:** `src/models/ChunkModel.py`

| Method | Job |
|--------|-----|
| `create_chunk` | Insert one chunk |
| `get_chunk` | Fetch by `_id` |
| `insert_many_chunks` | Insert many in **batches** (default 100) via `bulk_write` + `InsertOne` |
| `delete_chunks_by_project_id` | Delete all chunks for a project |

**Why batches?** Inserting thousands of chunks one request at a time is slow. Bulk ops send a batch per round-trip.

## Lesson 7 — Routes now persist data

**File:** `src/routes/data.py`

### Upload

1. `ProjectModel` + `get_project_or_create_one`  
2. Validate + save file to disk (same as before)  
3. Return success + `file_id` (still the **disk** filename in this session)

### Process

1. Read `file_id`, `chunk_size`, `overlap_size`, **`do_reset`**  
2. Ensure project exists  
3. Load + split (same `ProcessController` as tut-005)  
4. Map each LangChain chunk → `DataChunk(...)`  
5. If `do_reset == 1` → delete old chunks for that project  
6. `insert_many_chunks`  
7. Return `{ signal, inserted_chunks }` — **not** the full chunk list

**What changed philosophically?**  
`tut-005` returned the chunks as the response body (good for debugging).  
`tut-006` **stores** them and returns a summary. The database is now the source of truth for later RAG steps.

`do_reset` already existed on `ProcessRequest` in tut-005; this session is where it actually gets used.

## How the pieces fit (one diagram)

```text
FastAPI startup
    └── Motor client → db_client on app

POST /upload/{project_id}
    └── ProjectModel.get_or_create
    └── save file to disk

POST /process/{project_id}
    └── ProjectModel.get_or_create
    └── ProcessController → list of text chunks
    └── [optional] ChunkModel.delete by project
    └── ChunkModel.insert_many
    └── JSON: how many inserted
```
